# ИСУП Монитор

Парсер обходит реестр ОКС, открывает карточки объектов и выгружает участников из раздела «Управление проектами».

Для запуска укажите `ISUP_URL`, `ISUP_LOGIN` и `ISUP_PASSWORD` в файле `.env`.

```sh
uv run playwright install chromium
uv run isup-monitor > projects.json
```

Для пробного запуска добавьте `--limit 3`. Чтобы видеть окно браузера, добавьте `--headed`. Участники каждого объекта записываются в поле `participants`. Если список пуст, поле содержит `[]`. Если список прочитать не удалось, поле содержит `null`, а причина сохраняется в `participants_error`. Ошибки обхода также выводятся в stderr.

Чтобы получить 34 поля листа «Объекты» в порядке раздела 5.1 ТЗ, используйте режим отчёта.

```sh
uv run isup-monitor --report --limit 3 > objects-report.json
```

### Запись снимков в PostgreSQL

В Docker Compose приложение и PostgreSQL запускаются в отдельных контейнерах. Укажите в `.env` настройки ИСУП и значения `DB_USER`, `DB_PASS`, `DB_NAME`. В контейнере приложение подключается к `postgres:5432` и применяет миграции перед выгрузкой.

```sh
docker compose run --build --rm app --save-db --limit 1
```

Для полного обхода уберите `--limit 1`. В контейнере Chromium запускается в фоновом режиме. После выгрузки контейнер приложения завершает работу, а PostgreSQL продолжает работать и хранит снимки в Docker-томе.

#### Запуск парсера на хосте

Заполните в `.env` параметры `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASS` и `DB_NAME`. Для локальной базы задайте `DB_HOST=localhost` и запустите PostgreSQL через Docker Compose. Если у вас уже есть работающий сервер PostgreSQL, примените миграции на нём.

```sh
docker compose up -d --wait postgres
uv run alembic upgrade head
uv run isup-monitor --save-db
```

Для пробного запуска добавьте `--limit 1`. Объект сохраняется сразу после обработки карточки. Если обход завершён и есть записанные объекты, снимок получает `partial` при `--limit` или ошибках отдельных объектов, иначе `ready`. Причины остаются в журнале. Пустой или незавершённый обход получает `failed`. Для отчётов выбирается последний снимок со статусом `ready` или `partial`. Чтобы одновременно записать снимок и вывести JSON, добавьте `--report`.

Отчёт выгружается в JSON. Поля без подтверждённых данных остаются `null`. Команды и число людей читаются в разделе «Информационный обмен → Модуль заказчика (ЭДО)». Операции считаются по столбцу «Дата документа» в «Документации». Финансовые данные берутся из паспорта объекта. Если отдельного поля «Освоено» нет, используется сумма «Оплачено». Порог для вывода «нет обмена более N дней» задаётся параметром `--exchange-threshold` и по умолчанию равен 7.

### Пробная выгрузка без Chromium

```sh
uv run isup-monitor --http --report --limit 1
```

Для одновременной обработки до четырёх объектов добавьте `--concurrency 4`. По умолчанию объекты обрабатываются по одному. JSON сохраняет порядок реестра.

Режим `--http` получает реестр, часть полей карточки, проектные сроки, документацию и финансирование через HTTP-клиент Playwright. При ошибке чтения раздела выгрузка без записи в БД возвращает код 1. При запуске с `--save-db` завершённый неполный снимок получает статус `partial`, а команда возвращает код 0.

HTTP-парсер получает токен ЭДО через ИСУП и при ответе 401 обновляет его в ходе
выгрузки. Если задан `ISUP_EDO_TOKEN`, парсер использует его как начальный токен.
Участники, организации и подписи записываются в снимок при запуске с `--save-db`.

### Локальный API

Светофор рассчитывается при формировании снимка. Документы или доступный состав
ЭДО подтверждают отслеживание обмена. Приостановленным объектам присваивается серый.
Подтверждённые красные условия имеют приоритет. Пропуски обязательных полей
и сведения, которых недостаточно для исключения рисков, дают жёлтый.
Отсутствие роста СМР проверяется при сохранении в БД по ежедневным снимкам
за 56 дней. До накопления истории этот признак считается неизвестным.
Ранее сохранённые статусы автоматически не пересчитываются.

Запустите `docker compose up -d --build --wait api` и откройте Swagger по адресу
`http://localhost:8000/docs`. При необходимости задайте `API_PORT` в `.env`.

- `GET /health` проверяет запуск приложения.
- `GET /api/v1/projects` возвращает объекты последнего снимка со статусом `ready` или `partial`. Поддерживает фильтры `name`, `stage`, `state`, `customer`, `status` и параметры `offset`, `limit`.
- `GET /api/v1/projects/{oks_number}` возвращает поля отчёта по одному объекту.
- `GET /api/v1/projects/export.xlsx?snapshot_id=37` скачивает все доступные пользователю объекты выбранного снимка, включая листы участников, организаций, операций и помесячного обмена. Даты операций пока соответствуют полю «Дата документа» в ИСУП.
- `GET /api/v1/projects/{oks_number}/participants` возвращает участников и статусы подписей. Через `snapshot_id` можно выбрать конкретный снимок.
- `GET /api/v1/snapshots/latest` возвращает метаданные последнего снимка со статусом `ready` или `partial`.
- `GET /api/v1/ingestions` возвращает журнал запусков с пагинацией.

Маршруты объектов и снимка возвращают 404, пока нет снимка со статусом `ready` или `partial`. API использует сессию веб-приложения. Сначала войдите через Яндекс ID в том же браузере, в котором открыт Swagger.

### Веб-интерфейс

Откройте `http://localhost:8000/` после запуска `docker compose up -d --build --wait api`.
Для входа зарегистрируйте веб-приложение в Яндекс OAuth с правами `login:info` и `login:email` и добавьте в `.env`:

```dotenv
YANDEX_CLIENT_ID=
YANDEX_CLIENT_SECRET=
YANDEX_REDIRECT_URI=http://localhost:8000/auth/yandex/callback
YANDEX_CORPORATE_DOMAIN=
WEB_COOKIE_SECURE=false
```

Укажите корпоративный домен без `@`. Адрес callback должен совпадать с Redirect URI приложения Яндекс OAuth. Для HTTPS используйте `WEB_COOKIE_SECURE=true`. После обновления настроек пересоздайте контейнер API.

После первого входа веб-приложение показывает номер пользователя на гостевом экране. Оператор назначает первого администратора из консоли, подставив этот номер:

```sh
docker compose exec api python -m src.web.users.bootstrap 1
```

Остальные пользователи получают роль через раздел «Пользователи» после первого входа. Для РП и строительного заместителя администратор указывает закреплённые номера ОКС через запятую. Страница объектов читает последний снимок со статусом `ready` или `partial`. Для просмотра пробного снимка введите его номер в фильтре.

### Закрепления, регламент и история

Администратору доступны «Закрепления» и «Правила светофора».
Для импорта закреплений скачайте шаблон на странице, заполните его и загрузите XLSX.
Импорт обновляет перечисленные объекты целиком и проверяет файл до записи.
ФИО из ИСУП имеет приоритет, справочник сразу заполняет пропуски в отображении последнего снимка и применяется при следующих выгрузках. Исторические снимки сохраняют свои значения.
Аккаунты РП и заместителя связываются с email вошедшего пользователя соответствующей роли.
Ранее назначенные администратором права также действуют.

Новая версия регламента содержит дату начала действия, пороги и обязательные поля.
При запуске парсера версия закрепляется за снимком.
Начальные правила сохраняются с названием «ТЗ v3 (предварительные)».
Исторические статусы сохраняются с применённой версией.

После обновления контейнера API миграции применяются автоматически.
Для восстановления событий из старых снимков выполните:

```sh
docker compose exec api python -m src.web.events.backfill
```

Повторное восстановление не дублирует события.
Новые события характеристик, сроков, финансов, ответственных, статусов, организаций,
участников и документов записываются при завершении выгрузки.
Периоды без наблюдений отмечаются датой следующего снимка.
В карточке доступны фильтр хронологии по датам и типам, а также недельные графики.

Реестр поддерживает фильтры `manager`, `deputy`, `no_exchange`, `overdue`,
сортировку `sort`, направление `descending` и группировку `group`.
Все фильтры и экспорт сохраняют ограничения доступа.

### Проверка полноты источников

HTTP-сбор документации сохраняет исходную строку ИСУП, идентификатор документа
и автора, если ИСУП его вернула. В XLSX есть лист «Полнота данных» с замечаниями.
Некорректные email и значения `[object Object]` отмечаются при сохранении.
До подтверждения отдельного источника даты поступления операции считаются
по «Дате документа». Для соответствия разделам 5.4–5.4.1 ещё требуется
источник поступления, статусов отправки и регистрации ОЖР.
Сверка с эталонным XLSX и официальным регламентом требует документов заказчика.


### Документы ПД и РД

HTTP-парсер читает обе вкладки модуля ПИР через штатные постраничные запросы:
`project-documents/projects/page/{projectId}` и
`work-documents/projects/page/{projectId}`.
Документы сохраняются отдельно от операций обмена и отображаются в карточке
и на листе «Документы ПД и РД» в XLSX. Пустой список сохраняется как прочитанный
пустой раздел. Ошибки запроса записываются как `pir_error`.

Сохраняются шифр, название, раздел, версия, статус, даты создания,
согласования, передачи заказчику и выдачи в работу, количество замечаний.
Просрочка считается от плановой даты согласования до фактической даты
согласования, а до согласования — до даты выгрузки. При отсутствии плановой
даты просрочка остаётся пустой. Исходный ответ сохраняется вместе с документом.

## Управленческий Excel и подготовка данных для Алисы

Выгрузка начинается с листов «Сводка объектов» и «Проблемы». Дальше идут описание
данных, история изменений и подробные записи. У каждой строки есть номер снимка
и дата среза. В «Объектах» сохранены исходные 34 поля, метаданные добавлены справа.

Оценки проверок различаются:

- «Подтверждённая проблема»: например, у добавленной организации нет команды,
  участник не подписал приказ или текущий этап просрочен.
- «Факт для проверки»: признак отсутствует, но обязательность не установлена.
- «Не удалось проверить»: раздел не прочитан либо источник ещё не подключён.

Обязательные роли, ПД/РД и регистрация ОЖР настраиваются в новой версии правил
на странице «Правила светофора». По умолчанию обязательность не назначается.
Правила принадлежат снимку: новая версия применяется при следующем сборе.
Авторский надзор и стройконтроль не объявляются обязательными на всех объектах
без согласованного правила. Исключения отдельных объектов пока нужно учитывать
при проверке отчёта: настройки сейчас действуют на всю стадию.

### Получить файл из существующего снимка

В интерфейсе используйте «Скачать Excel» или ссылку в сводке. Права на объекты
сохраняются во всех листах, включая историю. Контакты доступны только разрешённым ролям.

Из консоли (без контактов, подключение к той же PostgreSQL):

```bash
uv run python -m src.web.exports.cli --snapshot-id 40
uv run python -m src.web.exports.cli --snapshot-id 40 --oks 3669 4836 4844
```

В Docker файлы сохраняются в отдельном томе `export_files`:

```bash
mkdir -p output/exports
docker compose run --rm --build --entrypoint python app -m src.web.exports.cli --snapshot-id 40
docker compose cp api:/app/output/exports/. ./output/exports/
```

По умолчанию локальные файлы находятся в `output/exports/`. Имя содержит дату
среза и номер снимка. Рядом сохраняется JSON с охватом, ограничениями и итогом
отправки на Диск. Эти файлы исключены из Git. Пробную выборку не следует принимать
за полный реестр. Книга ограничивается переданными номерами во всех листах.

### Собрать данные и сразу создать Excel

```bash
uv run isup-monitor --http --save-db --archive all --concurrency 4 --export-xlsx
```

Для пробного сбора добавьте `--limit 10`. Доступные режимы архива:
`active` (по умолчанию), `archived`, `all`. В HTTP-сборе архивность определяется
отдельным фильтром реестра; в старых снимках она может быть неизвестна.
Ошибки отдельных разделов не отменяют Excel завершённого снимка `partial`.
При ошибке экспорта снимок остаётся в БД, команда завершается с кодом 2;
повторите только `src.web.exports.cli`, без повторного парсинга.
Одновременно для одной БД выполняется только один парсер с `--save-db`.

### Расписание и Диск

Обычный запуск `docker compose up -d api` не запускает парсер или расписание.
Планировщик включается отдельной командой:

```bash
mkdir -p output/exports
docker compose --profile schedule up -d --build scheduler
```

Он запускает полный HTTP-сбор рабочих и архивных объектов и создаёт Excel.
Контейнеры пишут в том `export_files`, который сохраняется после `down` без `-v`.
Для копирования файлов на компьютер используйте команду `docker compose cp` выше.
По умолчанию — пятница 22:00, Asia/Krasnoyarsk. Настройки в `.env`:

```dotenv
ISUP_EXPORT_DIR=output/exports
ISUP_SCHEDULE_WEEKDAY=4
ISUP_SCHEDULE_HOUR=22
ISUP_SCHEDULE_MINUTE=0
ISUP_SCHEDULE_CONCURRENCY=4
ISUP_SCHEDULE_UPLOAD=false
YANDEX_DISK_FOLDER=
YANDEX_DISK_TOKEN=
```

День недели: понедельник 0, воскресенье 6. При остановленном контейнере
расписание не выполняется. После сбоя нужен ручной повтор; уведомления о сбое
и автоматический догон пропущенного запуска пока не реализованы.

До выдачи доступа к корпоративной папке оставьте отправку выключенной.
После подключения администратор задаёт OAuth-токен Диска в `.env` и существующую
папку `disk:/...`, проверяет права пользователей и доступ Алисы к файлу.
Токен входа через Яндекс ID и токен записи в Диск — разные подключения.
Ручная отправка готового снимка:

```bash
uv run python -m src.web.exports.cli --snapshot-id 40 --upload
```

Для планировщика отправка включается `ISUP_SCHEDULE_UPLOAD=true` с пересозданием
контейнера. Файлы не публикуются в общий доступ. Письма и поручения автоматически
не отправляются. При сбое доставки локальный XLSX остаётся доступным для повторной
отправки. Ответ 202 отмечается как «Принято Диском», а не как проверенная индексация
Алисой. Интеграция с Диском подготовлена, но без корпоративного доступа не проверена.

### Какие выводы пока делать нельзя

- Количество документов и дата документа не равны числу транзакций и времени
  последнего движения. Источник переходов, получателя и текущего исполнителя ещё нужен.
- Источник реестра исполнительной документации не подключён. «Нет данных» не
  означает, что ИД отсутствует.
- Наличие файла ПД/РД означает хотя бы один загруженный документ, а не полный комплект.
- Регистрация ОЖР проверяется по `titlePage.buildingInfo`: `signed=true`, номер и дата
  подтверждают регистрацию. `signed=false` без реквизитов означает отсутствие регистрации.
  `target-solution` не является статусом регистрации и не используется. Старые снимки
  без реквизитов показывают «Нет данных» до повторной проверки.
- Архивность и отсутствие обмена — разные признаки. «Наши» объекты выделяются
  по заказчику/согласованному списку, а не фиксированным числом из разговора.
- История показывает обнаружение изменения в снимке, не точную дату события.
  Папки не содержат выдуманных причин задержки, сроков поручения или виновников.

### Пример запроса корпоративной Алисе

«Используй листы книги и дату снимка. Выдели объекты заместителя [ФИО].
Раздели подтверждённые проблемы, факты для проверки и недостаток данных.
Для каждой проблемы укажи номер и название объекта, организацию, участника
при наличии, подтверждающий факт и рекомендуемое действие. Сошлись на лист
и код проверки. Не придумывай причины задержки, виновников и сроки. Если
готовишь письмо, пометь его как проект для проверки человеком».

Проверка: выбрать 5–10 известных объектов, сверить с ИСУП, затем проверить ответы
Алисы на вопросы по заместителю, организации и изменению между датами. Приёмку
автоматической аналитики считать выполненной только после такой сверки.
